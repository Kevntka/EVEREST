# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

EVEREST is an event registration system: an Angular 21 frontend plus a FastAPI + PostgreSQL backend.

## Repository layout gotchas

- **The real frontend is `frontend/event-registration/`.** It is a normal folder of this one repo (`github.com/Kevntka/EVEREST`); commit and push from the repo root. It used to be a separate git repo with the same remote and branch, whose pushes replaced the whole project on GitHub. Don't `git init` or clone into it again; its old `.git` is backed up in `../EVEREST-frontend-git-backup`. The old copy of the frontend that used to sit at the repo root (`src/`, `public/`, `angular.json`, `package.json`) was removed; the repo root has no Angular project.
- **The backend is `backend/`.** The active router is `backend/api/routes_db.py`. `backend/api/routes.py` is a legacy in-memory version that isn't mounted in `main.py`.
- The untracked leftovers `frontend/event-registration/backend/` and `frontend/event-registration/frontend/` (from the separate-repo days) and the stale `backend/tests/__pycache__` were deleted. The real backend is the root `backend/`; the test suite is the root `tests/`.
- `backend/` has two manual utility scripts, both using `DATABASE_URL` from `.env`: `python create_admin.py` creates an admin (a `users` row with `role = 'admin'` and no `user_roles` row; it prompts for name, email and a hidden password), and `python reset_database.py` truncates every table after you type the database name. `backend/database/schema.sql` starts with `DROP TABLE ... CASCADE`, so running it wipes all data.

## Commands

Frontend (run from `frontend/event-registration/`):

```bash
npm start                                  # ng serve on http://localhost:4200
npx ng build --configuration development   # quick compile check
npx ng build                               # production build; also enforces the size budgets in angular.json
npm test                                   # Vitest via ng test
npx ng test --watch=false                  # single run, no watch
npx ng test --include src/app/app.spec.ts  # single spec file
```

Backend (run from `backend/`. Imports and the `uploads/` path are relative to it):

```bash
venv\Scripts\activate                      # or: source venv/Scripts/activate (Git Bash)
python -m uvicorn main:app --reload        # http://localhost:8000; start_server.bat does this
```

Docker (run from the repo root; Docker Desktop must be running). `docker-compose.yml` runs three containers: `db` (`postgres:17-alpine`, data in the `db_data` volume, published on host port **5433** because the local PostgreSQL uses 5432), `backend` (`backend/Dockerfile`, uvicorn on `0.0.0.0:8000`, no `--reload`), and `frontend` (`frontend/event-registration/Dockerfile`: `ng build` in a Node stage, served by nginx with an SPA `try_files` fallback in `nginx.conf`, published on 4200). Ports 4200 and 8000 must stay as they are: the frontend hardcodes `localhost:8000`, and CORS, the Origin check, and the reCAPTCHA key expect `localhost:4200`. The backend gets `backend/.env` through `env_file` at run time (`.env` is in `.dockerignore`, never in the image), and Compose overrides its `DATABASE_URL` to point at `db` and sets `TZ: Asia/Manila` (containers default to UTC, and events open and auto-close by the server's local time). `schema.sql` is mounted into `/docker-entrypoint-initdb.d`, so it runs only when the volume is empty; `docker compose down -v` deletes the container database. The container database is separate from the local `ers_db`, so it starts with no admin. Containers hold a copy of the code, so changes need a rebuild; day-to-day development still uses `npm start` + `uvicorn --reload` (stop the containers first, same ports). `DOCKER_GUIDE.md` is a step-by-step Taglish tutorial for this setup.

```bash
docker compose up -d --build                         # build and start everything
docker compose exec backend python create_admin.py   # admin in the container database
docker compose logs -f backend                       # logs
docker compose down                                  # stop (keeps data); add -v to delete the database
```

End-to-end and API tests live in the repo-root `tests/` folder, **deactivated by request**: every test is skipped (and `run_load_test.py` exits) unless `EVEREST_TESTS_ENABLED=1` is set (switch at the top of `tests/conftest.py`) (Pytest + Playwright + Locust, own venv `tests/.venv`; see `tests/README.md`). They create and wipe a separate database `ers_db_test` (guarded: name must end in `_test` and differ from `backend/.env`), start the backend themselves on :8001 with test-only settings (random JWT secret, `EMAIL_ENABLED=false`, Google's reCAPTCHA test secret), and reroute the Angular app's `localhost:8000` calls to it in the browser tests. Run them with `run_tests.bat` / `tests/.venv/Scripts/python tests/run_tests.py [auth|api|functional|scheduling|security|e2e] [--failed] [-- pytest args]`, which prints a FAILED/ERROR table and writes `tests/reports/summary.txt`, appends to `tests/reports/history.csv`, and leaves `report.html`, `backend.log`, and e2e failure screenshots in `tests/reports/`. Plain `tests/.venv/Scripts/python -m pytest tests` also works (the Angular dev server must be on :4200 for `tests/e2e`; the script skips them when it isn't). Findings are in `tests/REPORT.md`. With `TEST_MAIL_SINK=1` the test backend sends real SMTP mail to a local catch-all server (`tests/helpers/mailsink.py`, STARTTLS with a throwaway localhost certificate trusted via `SSL_CERT_FILE`) instead of turning email off. `tests/e2e/test_zz_screenshots.py` (marker `screenshots`, skipped by default; run with `-m screenshots`) saves app screenshots per QA case to `tests/reports/screenshots/`. The user manual is a Claude Docs doc, not a repo file; its screenshots are in `tests/reports/manual/`. `backend/tests/` is empty. To check backend changes, use FastAPI's `TestClient` (`from fastapi.testclient import TestClient; import main`, run with `venv/Scripts/python` from `backend/`). It talks to the **real** database in `DATABASE_URL`, so stick to GET requests and requests that are rejected. POSTs also need a token from `GET /api/csrf-token` in `X-CSRF-Token` and an `Origin: http://localhost:4200` header. Set `PYTHONIOENCODING=utf-8` whenever backend output is piped or redirected (TestClient scripts, uvicorn in the background): the routes `print()` emoji, and on the Windows cp1252 encoding that raises `UnicodeEncodeError`, which fails the request. The rate-limit and login-lockout counters live in memory, so restarting the server clears them.

Configuration comes from `backend/.env` (loaded with python-dotenv; there is no `.env.example`, so this list is the reference): `DATABASE_URL`, `JWT_SECRET_KEY`, `SMTP_*`, `EMAIL_ENABLED`, `BREVO_API_KEY`, `RECAPTCHA_SECRET_KEY`, and the optional security settings `FRONTEND_URL`, `ALLOWED_ORIGINS`, `HTTPS_ONLY`, `ENABLE_API_DOCS`, and `SQL_ECHO`. All mail goes through `_send()` in `services/email_service.py`. It uses Brevo's HTTPS API when `BREVO_API_KEY` is set and SMTP otherwise. The campus network ("BatStateU ICT") blocks every outbound SMTP port (587, 465, 2525), so SMTP only works on other networks. The schema is in `backend/database/schema.sql`.

**Database connections under load.** `get_db` (`database/config.py`) is an `async` generator and the pool is 20 + 30 connections; `database/concurrency.py` (`DatabaseConcurrencyLimit`, added in `main.py`) lets at most `MAX_DB_REQUESTS` = 40 `/api` requests run at once. Keep `MAX_DB_REQUESTS` below the pool size and at most FastAPI's 40 worker threads: a request keeps its connection while hopping between threads (`current_user`, then the route), and without the cap the server deadlocked at ~250 users (pool timeouts, HTTP 500). Load test for many users: `tests/.venv/Scripts/python tests/performance/run_load_test.py --steps 100,250,500,1000 --spawn-rate 25 --attendees 1200 --login token --locust-workers 4` (results in `tests/REPORT.md`).

## Architecture

**Roles and pages.** There are four roles: `admin`, `organizer`, `student`, and `participant`. Each role has its own set of standalone page components under `src/app/components/`:
- Admin: `dashboard`, `organizer`, `students`, `participants`. Admins must be able to **view, edit, and delete** events, organizers, students, and participants: every admin table row has View, Edit, and Delete, and every delete asks `dialog.confirm` first. Dashboard (events): View opens the shared `/event/:id` page (`event-details`, `authGuard` only); Edit opens `<app-event-edit-modal>` (`components/event-edit-modal/`, a copy of the organizer-events form, which keeps its own Create/Edit modal); Delete calls `DELETE /api/events/{id}`. Students and Participants: View opens a read-only details modal; Edit opens an Edit modal that calls `PUT /api/students/{id}` / `PUT /api/participants/{id}` (JSON: the Profile page's fields plus `email`, validated by the same `_apply_profile()` the Profile page uses); Delete calls `DELETE /api/students/{id}` / `DELETE /api/participants/{id}`. Organizer: View (the same details modal), Edit (`PUT /api/organizers/{id}`), and `DELETE /api/organizers/{id}`, which also deletes their events. The Students/Participants Edit modal styles are in `components/admin-table.css` (see Styling conventions). These endpoints are `admin_only`, except `PUT`/`DELETE /api/events/{id}`, which organizers may also call on their own events.
- Organizer: `organizer-dashboard`, `organizer-events`. Each event row's Action column has View, Attendance, Edit, and Delete. View opens a read-only modal on the page showing only what the organizer entered in the Create Event form, not the shared `/event/:id` page. It uses the same design as the admin View modals (`.details-modal`: rounded-rectangle 120×68 cover thumbnail or initial, title, venue, icon rows, full-width Close; no badge; Description/About show their full text under the label) so all View modals look alike; View and Edit use the same gray-blue as the admin buttons. There is no Attendance page: the **Attendance** button in an event's Action column opens a modal on `organizer-events` listing that event's attendees with Present / Not Recorded buttons (`GET /api/organizer/attendees?event_id=...`, which returns only that event's enrollees in the organizer's own events).
- Student and participant: `student-dashboard`, `student-profile` (participants see name, address, birthday, gender, and contact number instead of the student fields), `my-events`, `event-details`. `my-events` reuses `student-dashboard.css` and loads data from `GET /api/student/my-events`, which uses the login cookie.

Each page component contains its own sidebar, top bar, and modals. There is no shared layout component, so a UI change to one page usually has to be repeated on its sibling pages.

**Change detection.** The app is zoneless: there's no zone.js, so views don't update on their own after async work. For HTTP responses, `interceptors/change-detection.interceptor.ts` (registered in `app.config.ts`) calls `markForCheck()` on the root components after each request's subscribe callbacks. Don't switch this to `ApplicationRef.tick()`: in zoneless mode, `tick()` skips views that aren't marked dirty. Its spec is the regression test. The event pages (admin Dashboard, Organizer Dashboard and Events, Student Dashboard, My Events, Event Details) re-fetch every 10 seconds with `autoRefresh()` (`utils/auto-refresh.ts`, called from a field initializer), so Open/Full/Closed/Upcoming change live. Its callbacks make HTTP calls, so the interceptor handles the redraw. Other async sources, such as `setTimeout` or third-party callbacks, still need `ChangeDetectorRef.detectChanges()` or signals. Some components also call `cdr.detectChanges()` after HTTP responses. That code predates the interceptor and is now redundant, but it does no harm.

**API calls.** Components call `HttpClient` directly with hardcoded `http://localhost:8000/api/...` URLs. There is no API service layer. The backend's CORS setting only allows `ALLOWED_ORIGINS` (default `localhost:4200`). Most endpoints take `multipart/form-data` (FastAPI `Form(...)`), so the frontend sends `FormData`.

**Authentication**
- `POST /api/login` verifies the reCAPTCHA token and sets an HTTP-only `access_token` JWT cookie.
- The frontend separately stores `userRole`, `userName`, `userId`, and, for organizers, `organizerId`/`organizerName` in `localStorage`.
- The route guards in `guards/auth.guard.ts` read only `localStorage`; they only decide which pages show. The backend is the real check.
- **Access control** (`backend/security/access_control.py`). Every endpoint except login, register, verify/resend, forgot/reset password, `csrf-token`, logout, and the event cover image requires the login cookie. Routes declare who may call them with `Depends(require_roles(...))` (`admin_only`, `organizer_only`, `attendee_only` = student/participant, or `current_user` for any role). The dependency loads the `User` row, so deleted accounts and role changes take effect at once. The JWT carries `pwd`, a fingerprint of the password hash, so a password change or reset logs out every older session. Organizer endpoints use the cookie's user: the `organizer_id` form field / query parameter the frontend still sends is ignored. Organizers can edit or delete only their own events and mark attendance only on their own events; admins can edit or delete any event. `GET /api/events` returns every event to admins, students, and participants, but only the logged-in organizer's own events to an organizer (their Events page).
- **Frontend interceptors** (`app.config.ts`): `auth.interceptor.ts` sends every `http://localhost:8000/api` request with credentials (so components don't need `withCredentials`) and, on a 401 from anything but `/api/login`, signs out through `SessionService`. `csrf.interceptor.ts` fetches `GET /api/csrf-token` once and adds `X-CSRF-Token` to every POST/PUT/PATCH/DELETE, refetching and retrying once on a 403 with `csrf_failed`. Their spec is `interceptors/security.interceptors.spec.ts`.
- **Sign Out** on every page calls `SessionService.signOut()`, which clears localStorage and calls `POST /api/logout` (the only way to delete the HTTP-only cookie). Logout also **revokes the token on the server**: every JWT has a unique `jti`, logout stores it in the `revoked_tokens` table (created by `schema.sql` and by the `main.py` startup hook; rows are purged once the token would have expired), and `current_user` rejects revoked tokens and tokens with no `jti`. Signing out ends only that session, not the user's other devices.
- **Change Password** (user dropdown on every organizer/student/participant page) has no form: `ChangePasswordService.sendLink()` confirms, then `POST /api/change-password` emails a Set New Password link to the cookie user's own email. It is the same one-hour `/reset-password?token=...` link Forgot Password sends (`_send_reset_link()` in `routes_db.py`). Only the SHA-256 of reset tokens is stored in `password_reset_tokens.token`. A successful reset marks all of the user's unused links as used. After a successful reset, the reset page signs out any logged-in session.
- **Other security middleware** (`backend/security/`, added in `main.py`; CORS is added last so 403/429 responses still carry CORS headers): `csrf.py` (Origin check plus signed double-submit token for unsafe methods on `/api`), `rate_limit.py` (in-memory: 600 API requests/min **per logged-in user** (keyed by the JWT's `user_id`; per IP for requests without a valid login cookie), because campus users share one public IP; per-IP limits on login (100/min), register and verify-email (60 per 10 min), email-sending and token endpoints; and a 15-minute lock after 5 wrong passwords for one email), `headers.py` (nosniff, frame DENY, CSP, CORP, and with `HTTPS_ONLY=true` an HTTPS redirect and HSTS), `errors.py` (added first, so innermost: turns any unhandled exception into a JSON 500 `{"detail": ...}` that still gets CORS headers; the traceback only goes to the server log), `validation.py` (server-side checks for text lengths, email, phone, tokens, and uploaded images by magic bytes; SVG is rejected), and `settings.py` (the server won't start without `DATABASE_URL` and a 32+ character `JWT_SECRET_KEY`). `EXPLANATION.md` at the repo root explains each one. Testing with curl now needs a CSRF token: GET `/api/csrf-token` with a cookie jar, then send its value as `X-CSRF-Token` along with `Origin: http://localhost:4200`.
- **Status codes:** duplicates (email or Employment ID already used, already enrolled, already verified) return **409**; other bad input 400 (or FastAPI's 422 for missing/wrong-type fields). The Verify Email page relies on 409 for "already verified".
- HTML emails escape user-entered values with `html.escape`.
- reCAPTCHA v2 "I'm not a robot" Checkbox: the public site key is hardcoded in `login.ts` (`recaptchaSiteKey`), the secret is `RECAPTCHA_SECRET_KEY` in `backend/.env`. Both must come from the same v2 Checkbox key pair (a v3/Invisible key shows "Invalid key type"), with `localhost` in the key's domains. The login page renders one widget per theme and toggles visibility, so fast dark-mode toggling can't lose it.

**Data model** (`backend/models/user.py`, mirroring `schema.sql`)
- `users` holds identity, including the `role` string. `user_roles` holds per-role details: department, employment ID, and contact number.
- `events.user_role_id` references `user_roles.id`, not `users.id`. To link an event to an organizer, look up the organizer's `user_roles` row.
- `registrations.user_id` and `events.user_role_id` have **no** `ON DELETE CASCADE`. The delete endpoints for students, participants, and organizers remove those rows first; deleting an organizer also deletes their events. `registrations` cascade from `events`, and `attendees` cascade from `registrations`.
- **Self-registration and email verification.** Students, participants, and organizers all register themselves; admins don't create accounts (the admin Organizer page only edits and deletes). Organizers sign up at `/register/organizer` (`register-organizer`, whose department field is labeled "Office/Department" since organizers may belong to an office; it is still the `department` field, with its own compact `register-organizer.css` so 7 fields fit a laptop screen at 100% zoom), linked by "Are you an organizer? Register here" at the bottom of the login card; there is no admin approval. Sign-ups are not created in `users` until verified. Registering saves the details (with the bcrypt password hash) in `pending_registrations` and emails a **Verify Account** link (`http://localhost:4200/verify-email?token=...`); there is no code to type. The SHA-256 of the token is stored in the `code_hash` column (the `attempts` column is unused). Opening the link makes the `verify-email` page call `POST /api/verify-email` with the token, which creates the `users` and `user_roles` rows and deletes the pending row. Links expire after 24 hours; resending (`POST /api/resend-verification`) replaces the link and is limited to once per 60 seconds; pending rows older than 24 hours are purged. Unverified sign-ups therefore never appear in admin lists or counts. Login with a pending email and the correct password returns 403 with `verification_required`, and the frontend redirects to `/verify-email?email=...&resend=1`, which sends a fresh link. Organizer sign-ups also store `employment_id` in `pending_registrations` (unique, checked again at verify time). That column is added by a startup hook in `main.py` (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`), since there are no migrations. Admins don't use this. `users.is_active` is a BOOLEAN column.
- **Password rules are required for new passwords** (product decision; they used to only be rated). The rules in `utils/password-policy.ts` are: at least 8 characters, an uppercase letter, a lowercase letter, a number, and a symbol, which can be **any** character that isn't a letter (any language), number, or space (e.g. `! @ # $ % ^ & *`; frontend `/[^\p{L}\p{N}\s]/u`, backend `not c.isalnum() and not c.isspace()`). All must be met in the three registration forms, Reset / Set New Password, and `create_admin.py`. The frontend checks `isStrongPassword()` and shows `PASSWORD_REQUIREMENT_MESSAGE`; the backend's `validate.new_password()` (`security/validation.py`) enforces the same rules with the same message. Login uses `validate.password()`, which only rejects empty passwords and ones over 128 characters, so accounts created before the rules can still sign in. `<app-password-checklist>`, under each confirm-password field, shows a strength bar (Weak, Fair, Good, Strong) and a "Required: ..." note that turns green when every rule is met.
- `user_roles` also holds the profile fields `gender`, `year_level`, `program`, and (for participants) `address` and `birthday` (DATE), edited on the Profile page.
- **Enrollment and capacity:** `enroll_event` locks the event row with `SELECT ... FOR UPDATE` before counting registrations, so concurrent enrollments can't overbook an event, even with several workers. It must stay a plain `def`: as `async def` (with its blocking DB calls) a request waiting for the lock froze the event loop, so the lock holder's session could never close (deadlock). Many other routes are still `async def` with blocking DB calls; don't add row locks to those without converting them.
- **Attendance** lives in `attendees` (`present` or `not_recorded`; there is no Absent option), and a row is created only when the organizer marks someone. Endpoints report a registration with no `attendees` row as `'pending'` (shown as "Pending" on My Events), so "Not Recorded" only appears when the organizer chose it.
- Some endpoints use ORM models; others (events) use raw `text()` SQL.
- Event dates are serialized as `YYYY-MM-DD` strings, and the frontend compares them as strings.
- **Event times and auto-close.** The organizer form's single Time field has a start and an end input (`events.event_time`, `events.event_end_time`). `_close_finished_events()` in `routes_db.py` sets `status = 'closed'` on open events whose end time (or start time, or end of day) has passed, using the server's local time. It runs before events are listed, fetched, enrolled in, and in organizer stats and My Events. Editing an event re-opens or closes it to match the new end time. **No events in the past:** a new event must end in the future and its registration dates can't be before today, so it is never created already Closed. The date pickers' `min` is today (`minPickableDate()`), and `pastScheduleError()` (`utils/event-time.ts`, used by the organizer Create/Edit form and the admin `event-edit-modal`) and `_reject_past_schedule()` in `routes_db.py` enforce the same rules. When editing, only the date, end time, or registration date that changed is checked, so an event that already happened can still be edited (e.g. a typo fix) but not moved to another past time. The frontend shows times with `utils/event-time.ts` (`8:00 AM - 5:00 PM`).
- Event cover photos are stored in the database: the bytes go in `events.cover_photo_data` (BYTEA) and the MIME type in `cover_photo_type`, with a 5 MB limit. The organizer form accepts photos up to 25 MB and shrinks them in the browser first (`utils/image-resize.ts`: max 1920px on the long side, WebP or JPEG; GIFs are left as is and must be under 5 MB). They're served by `GET /api/events/{id}/cover`. `events.cover_photo` holds that URL path, and the frontend prefixes it with `http://localhost:8000`. An event without one shows the title's first letter on a random color (`utils/cover-placeholder.ts`): picked per title on first display and cached until the app reloads, so it doesn't change on redraws or auto-refresh. `backend/uploads/` and the `/uploads` static mount are leftovers from the old file-based storage.

## Styling conventions

- **Dark mode.** `ThemeService` toggles `body.dark-mode` and saves the setting in `localStorage`. The global `body.dark-mode ...` rules in `src/styles.css` lose to Angular's encapsulated component styles, so dark-mode overrides must go in the component CSS as `:host-context(body.dark-mode) .selector`. Selectors that use `[data-theme="dark"]` never match anything.
- **Primary buttons** everywhere (Add, Create, Log In, Register, Enroll, View Details, dialog OK, and so on) use the same red: `#dc3545`, `#c82333` on hover, and `#f5c6cb` when disabled. Secondary buttons (Cancel, Edit/View in admin tables, Present/Not Recorded) stay gray or tinted.
- **Dark palette** (from the admin pages): page `#1a1a1a`; cards and tables `#2d2d2d`; row hover `#3a3a3a`; borders `#404040`; table text `#ffffff`; accent red `#dc3545`.
- **Table pages** (admin Dashboard, Organizer, Students, Participants, Organizer Events, and My Events) share one layout. The page content has the `page-fill` class and the table sits in a `.table-scroll` wrapper inside `.table-container`; the shared rules are in `styles.css`. The card fills the screen, rows scroll under a pinned header row, and the pagination stays at the bottom. Every list table has `min-width: 760px` (set in `styles.css`, and in `my-events.css` for My Events, overriding each page's own min-width): on wide screens it fills the card with no scrollbar, and on narrow screens it keeps its width and scrolls sideways instead of squeezing the columns. Empty and loading messages go in a `<div class="table-empty">` after the `</table>` so they center in the table area. Rows are paged 10 at a time with `Paginator` (`utils/paginator.ts`): `*ngFor="let x of pager.slice(list)"`. The `.pagination-btn` / `.pagination-info` styles (light and dark) live only in `styles.css`; don't redefine them in component CSS.
- **Admin table action buttons** are 36px icon-only buttons whose label slides out on hover, always in the order View, Edit, Delete, in the original admin colors: View and Edit gray-blue (`#dbe4ee`), Delete light red (`#fee2e2`), with the dark-mode versions `#374151` and `#7f1d1d`. Keep these colors; don't color-code the buttons. They're defined **only** in `components/admin-table.css`, which the four admin pages list second in `styleUrls` (`['./page.css', '../admin-table.css']`); don't add `.action-btn` / `.view-btn` / `.edit-btn` / `.delete-btn` rules to page CSS. That file also fixes the Action column at 212px, so hovering doesn't shift the table. The organizer's own `organizer-events` page still has its own button styles.
- **Create/Add modals** have Cancel and Create buttons, don't close on backdrop click, and use `backdrop-filter: blur(...)` on the overlay.
- **Input `pattern="..."` is checked twice**: by the browser, which compiles it with the `v` flag (escape `-` inside `[...]`, or the whole pattern is ignored with a console error), and by Angular's `Validators.pattern`, which compiles it without `u` (so `\p{L}` doesn't work; list ranges like `A-Za-zÀ-ÖØ-öø-ÿ`). Admin Edit Organizer must accept what `/register/organizer` accepts (e.g. `EMP-0123`, `Juan D. O'Neil`).
- **Search bars** (admin Organizer/Students/Participants, organizer Events and its Attendance modal, Student Dashboard, My Events) all filter with `matchesSearch()` from `utils/search.ts` (case-insensitive, ignores leading/trailing and repeated spaces). Use it for any new search. `components/search-bars.spec.ts` types into each page's search bar and checks the rows that remain.
- **Dropdowns.** Use `<app-select>` (`components/select/select.ts`) instead of a native `<select>`, whose option list is drawn by the browser and can't be styled (in phone emulation it pops up huge, outside the page). It works with `[(ngModel)]`, takes `[options]` as `{ value, label }[]` and an optional `placeholder`, and draws its own arrow. Give it the page's old select class (e.g. `class="department-select"`) so the page CSS styles the box. No native `<select>` is left in the app. Its option list has no visible scrollbar (it still scrolls; arrow keys keep the highlighted option in view) and normally grows wider than the box for long labels; to keep it exactly as wide as the box (long labels end in "...", full text on hover), override `::ng-deep .panel { width: calc(100% + 2px); max-width: none; }` under the page's select class, as the organizer dashboard's `.attendance-filter` does.
- **Confirmations and notices.** Use `DialogService` (`services/dialog.service.ts`) instead of `window.confirm` or `alert`. It is rendered once by `<app-dialog-host>` in `app.html`. `await dialog.confirm('Warning', 'Are you sure you want to delete this ...?')` is the only dialog with buttons (Cancel and OK), and it resolves to a boolean. `dialog.success('Success!' | 'Deleted!', ...)`, `dialog.warning(...)`, and `dialog.error(...)` are notices with no buttons: they stay open until the user clicks anywhere or presses Escape. Messages may contain `\n`. Every page uses it; there are no `alert()` or `confirm()` calls left.
